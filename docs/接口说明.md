
### **API 端口设计规格说明**

本文档将阐述 Docker Registry Lite 服务中，每一个核心 Docker Registry V2 API 端口的设计与实现。

#### **1. 基础 API (Base API)**

##### **`GET /v2/`**

* **功能**:
  此端口作为初始的“握手”或 API 版本检查。它允许 Docker 客户端在执行任何其他操作之前，验证目标 URL 是否指向一个支持 V2 协议的 Registry。
* **设计与实现**:
  该设计有意地保持了简单和无状态。对应的处理器（`handleBase`）不与存储层交互。其唯一职责是返回 `200 OK` 状态码，并在响应头中包含关键的 `Docker-Distribution-Api-Version: registry/2.0`。此响应头是 V2 兼容性的主要信号。

---

#### **2. 清单 API (Manifests API)**

##### **`GET /v2/{name}/manifests/{reference}`**

* **功能**:
  获取镜像清单（manifest）或清单列表（manifest list）。这是 `docker pull` 流程的主要入口点。`reference` 可以是标签（如 `latest`）或摘要（如 `sha256:...`）。
* **设计与实现**:
  处理器（`handleManifestGet`）将核心逻辑委托给存储层（`storage.GetManifest`）。存储函数的设计能够“感知 reference 的类型”：
  1. 检查 `reference` 是标签还是摘要。
  2. 如果是标签，它通过读取文件系统上的 `link` 文件，将标签解析为其对应的摘要。
  3. 最终，它总是使用解析出的摘要从全局 Blob 存储中获取内容。
  4. 一个关键的设计特性是其**动态的 Content-Type 检测**。它会部分解析获取到的 JSON 内容以读取 `mediaType` 字段，从而确保为单架构清单和清单列表都能准确返回正确的 `Content-Type`。

##### **`HEAD /v2/{name}/manifests/{reference}`**

* **功能**:
  检查清单是否存在并获取其元数据（如 `Content-Length` 和 `Docker-Content-Digest`），而无需下载实际内容。客户端使用此功能进行优化。
* **设计与实现**:
  此设计镜像了 `GET` 端口的逻辑。`handleManifestHead` 执行与 `GET` 完全相同的 `storage.GetManifest` 调用以获取所有必要信息。然后，它设置与 `GET` 请求完全相同的响应头。唯一的区别是它省略了写入响应体的步骤，严格遵守 HTTP `HEAD` 请求的语义。

##### **`PUT /v2/{name}/manifests/{reference}`**

* **功能**:
  上传清单或清单列表，将其与一个标签或摘要关联。这是 `docker push` 工作流中最后也是最关键的一步。它还实现了题目中关于自动创建和维护清单列表的要求。
* **设计与实现**:
  这是最复杂的端口，以“验证优先”为原则设计，以实现最大程度的数据完整性。
  1. **依赖验证**: 处理器首先解析请求体，提取所有被引用的 Blob 摘要（`config` 和 `layers`）。然后遍历它们，为每一个都调用 `storage.StatBlob`，以确保所有依赖项都已上传。若有任何依赖缺失，整个操作将被拒绝并返回 `400 Bad Request`。
  2. **智能的 Manifest List 处理**: 核心逻辑被封装在 `storage.PutManifest` 中。该函数会检查标签是否已存在。
     * 若不存在，则创建一个指向新清单的新标签。
     * 若已存在，它会读取现有内容。如果新旧清单的平台不同，它会自动创建一个新的 `manifest list`，将两个清单都加入其中，将此列表保存为一个新 Blob，并更新标签指向这个新列表。如果平台相同，则替换列表中的现有条目。
  3. **健壮的存储**: 在此过程中创建的所有新 Blob（清单本身和任何生成的清单列表）都使用健壮的 `Create->Write->Sync->Close` 模式写入磁盘，以防止写缓存导致的数据损坏。
  4. 成功的响应是 `201 Created`，并附带一个指向清单不可变 URL（由摘要指定）的 `Location` 头。

##### **`DELETE /v2/{name}/manifests/{reference}`**

* **功能**:
  从仓库中移除一个清单。
* **设计与实现**:
  此端口的设计是一个**有意的简化**。官方规范要求通过摘要进行删除，这需要一个复杂且高风险的引用计数机制。
  * 我们的实现**拒绝**通过摘要删除的请求，并返回 `405 Method Not Allowed`，明确传达此功能不受支持。
  * 它提供了一个非标准但非常实用的替代方案：如果 `reference` 是一个标签，它会执行一个安全的“取消标签”操作，即简单地删除对应的 `link` 文件。这不会删除任何底层的 Blob 数据。

#### **3. Blob API**

##### **`GET /v2/{name}/blobs/{digest}`**

* **功能**:
  下载一个 Blob（镜像层或配置对象）。这是 `docker pull` 流程的核心主力。
* **设计与实现**:
  此设计为性能和低内存占用进行了优化。
  * 处理器（`handleBlobGet`）调用 `storage.GetBlob`，该函数返回一个 `io.ReadCloser`（文件句柄），而不是完整的文件内容。
  * 然后，它使用 `io.Copy` 将文件内容从磁盘**流式传输**到 HTTP 响应写入器。这确保了即使对于非常大的 Blob（GB 级别），服务的内存占用也保持在最低水平。
  * 它设置 `Content-Type: application/octet-stream` 和一个正确的 `Content-Length` 头。

##### **`HEAD /v2/{name}/blobs/{digest}`**

* **功能**:
  检查 Blob 是否存在并获取其大小。客户端使用此功能来避免重新上传已存在的内容。
* **设计与实现**:
  这是一个轻量级操作。处理器简单地调用 `storage.StatBlob`，后者执行一个文件系统的 `stat` 调用。如果成功，它返回 `200 OK` 并附带 `Content-Length` 和 `Docker-Content-Digest` 头。

#### **4. Blob 上传 API (Blob Uploads API)**

##### **`POST /v2/{name}/blobs/uploads/`**

* **功能**:
  启动一个新的 Blob 上传会话，或执行跨仓库挂载。这是上传 Blob 的第一步。
* **设计与实现**:
  处理器（`handleBlobUploadStart`）设计有两条清晰的逻辑路径：
  1. **挂载路径**: 如果请求包含 `mount` 和 `from` 查询参数，它首先尝试挂载。利用我们的内容寻址存储，这被简化为一次 `storage.StatBlob` 调用。如果 Blob 已存在于 Registry 的任何位置，挂载成功，并返回 `201 Created` 响应，其 `Location` 头指向最终的 Blob 位置。
  2. **上传路径**: 如果没有挂载请求，或挂载失败，处理器则回退到创建新的上传会话。它调用 `storage.StartUpload` 创建一个临时目录，并返回 `202 Accepted` 响应。其 `Location` 头指向由 UUID 标识的新的临时上传 URL。

##### **`GET /v2/{name}/blobs/uploads/{uuid}`**

* **功能**:
  获取一个进行中上传的状态，主要是确定已接收的字节数。这对于实现可续传上传至关重要。
* **设计与实现**:
  处理器调用一个专用的 `storage.StatUpload` 函数，该函数获取临时 `data` 文件的大小。其设计的关键在于响应：它返回 `204 No Content` 状态码。所有必要信息都在响应头中传达，特别是 `Range` 头（例如 `0-999`），它指明了已成功存储的字节范围。

##### **`PATCH /v2/{name}/blobs/uploads/{uuid}`**

* **功能**:
  向一个已存在的上传会话上传一个数据块。
* **设计与实现**:
  为效率和数据安全而设计。处理器将请求体直接流式传输给 `storage.AppendChunk`。此存储函数以 `append` 模式打开临时 `data` 文件，这是一种安全地并发添加数据的方式。关键的是，在写入后，它会执行 `file.Sync()` 来强制将数据从操作系统缓冲区刷新到磁盘，以防止数据完整性问题。它返回 `202 Accepted` 响应并附带更新后的 `Range` 头。

##### **`PUT /v2/{name}/blobs/uploads/{uuid}`**

* **功能**:
  完成一个 Blob 上传。客户端发出信号表示所有数据已发送完毕，并提供最终的摘要以供验证。
* **设计与实现**:
  这是 Blob 完整性的最后一道关卡。
  1. 处理器（`handleBlobUploadCommit`）首先处理请求体中可能存在的最后一个数据块。
  2. 然后调用 `storage.CommitUpload`，后者执行最关键的步骤：读取整个临时文件，计算其 SHA256 摘要，并与客户端提供的摘要进行比较。
  3. 如果摘要匹配，它执行一次原子性的 `os.Rename` 操作，将文件移动到其最终的内容寻址位置。如果不匹配，则返回 `400 Bad Request`。
  4. 成功后，它返回 `201 Created` 响应，其 `Location` 头指向最终的 Blob URL。

##### **`DELETE /v2/{name}/blobs/uploads/{uuid}`**

* **功能**:
  取消一个进行中的上传会话并清理所有临时数据。
* **设计与实现**:
  一个直接的清理操作。处理器调用 `storage.CancelUpload`，该函数对与 UUID 关联的临时上传目录执行 `os.RemoveAll`。它返回 `204 No Content` 响应以表示成功删除且无返回内容。
