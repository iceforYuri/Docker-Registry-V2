# 数据结构说明

本文档详细描述了 Docker Registry Lite 项目中的数据存储结构、文件系统布局和数据流转机制。

## 文件系统存储布局

Docker Registry Lite 采用与官方 Docker Registry 兼容的文件系统布局，所有数据存储在 `REGISTRY_STORAGE_ROOT` 环境变量指定的根目录下。

### 总体目录结构

```
{REGISTRY_STORAGE_ROOT}/
└── docker/
    └── registry/
        └── v2/
            ├── blobs/                    # 所有 Blob 数据的内容寻址存储
            │   └── sha256/               # 按 SHA256 算法分类
            │       ├── ab/               # 按 digest 前两位分子目录
            │       │   └── ab123...      # 实际的 blob 文件
            │       ├── cd/
            │       │   └── cd456...
            │       └── ...
            └── repositories/             # 按仓库组织的元数据
                ├── library/              # 命名空间（可选）
                │   └── alpine/           # 仓库名
                └── mycompany/
                    └── myapp/
                        ├── _manifests/   # Manifest 相关数据
                        └── _uploads/     # 临时上传会话
```

### Blob 存储详解

#### 存储路径规则

```go
// Blob 存储路径计算逻辑
func getBlobPath(digest string) string {
    // digest 格式: "sha256:abcdef123456..."
    hash := digest[7:]  // 去除 "sha256:" 前缀
    
    // 路径格式: blobs/sha256/{前两位}/{完整hash}
    return fmt.Sprintf("blobs/sha256/%s/%s", hash[0:2], hash)
}
```

**示例**:
- Digest: `sha256:abcdef123456789...`
- 存储路径: `blobs/sha256/ab/abcdef123456789...`

#### 为什么按前两位分目录？

1. **文件系统性能**: 避免单目录下文件过多导致的性能问题
2. **均匀分布**: SHA256 的前两位提供 256 种组合，确保相对均匀的分布
3. **兼容性**: 与官方 Docker Registry 保持一致

#### Blob 类型

在 Docker Registry 中，Blob 包含以下类型的数据：

1. **镜像配置 (Image Config)**
   - 包含镜像的元数据、环境变量、默认命令等
   - 媒体类型: `application/vnd.docker.container.image.v1+json`

2. **文件系统层 (Layer)**
   - 包含镜像的文件系统变更（通常是 tar.gz 格式）
   - 媒体类型: `application/vnd.docker.image.rootfs.diff.tar.gzip`

### Repository 元数据存储

每个仓库在 `repositories` 目录下都有独立的目录结构：

```
repositories/{repository-name}/
├── _manifests/
│   ├── revisions/           # 按 digest 存储的 manifest 版本
│   │   └── sha256/
│   │       ├── ab/
│   │       │   └── ab123.../
│   │       │       └── link # 包含实际的 manifest 内容
│   │       └── cd/
│   │           └── cd456.../
│   │               └── link
│   └── tags/                # 标签到 digest 的映射
│       ├── latest/
│       │   └── current/
│       │       └── link     # 包含指向的 manifest digest
│       ├── v1.0/
│       │   └── current/
│       │       └── link
│       └── stable/
│           └── current/
│               └── link
└── _uploads/                # 临时上传会话
    ├── 12345678-1234-1234-1234-123456789abc/
    │   ├── data             # 正在上传的数据
    │   └── startedat        # 上传开始时间戳
    └── 87654321-4321-4321-4321-cba987654321/
        ├── data
        └── startedat
```

### Manifest 存储机制

#### 1. Manifest 内容存储

```
_manifests/revisions/sha256/{digest前两位}/{完整digest}/link
```

**文件内容**: 完整的 Manifest JSON 数据

**示例**:
```json
{
    "schemaVersion": 2,
    "mediaType": "application/vnd.docker.distribution.manifest.v2+json",
    "config": {
        "mediaType": "application/vnd.docker.container.image.v1+json",
        "size": 1469,
        "digest": "sha256:config_digest_here"
    },
    "layers": [
        {
            "mediaType": "application/vnd.docker.image.rootfs.diff.tar.gzip",
            "size": 2797612,
            "digest": "sha256:layer1_digest_here"
        }
    ]
}
```

#### 2. 标签映射存储

```
_manifests/tags/{tag_name}/current/link
```

**文件内容**: 指向的 manifest digest（不包含 "sha256:" 前缀）

**示例文件内容**:
```
sha256:abcdef123456789...
```

### 上传会话管理

#### 临时上传目录结构

```
_uploads/{upload-uuid}/
├── data              # 累积的上传数据
└── startedat         # ISO 8601 格式的开始时间
```

#### 上传流程中的数据变化

1. **POST 开始上传**:
   ```
   创建目录: _uploads/{uuid}/
   创建文件: _uploads/{uuid}/startedat
   创建空文件: _uploads/{uuid}/data
   ```

2. **PATCH 追加数据**:
   ```
   追加到文件: _uploads/{uuid}/data
   ```

3. **PUT 完成上传**:
   ```
   验证 digest: sha256(_uploads/{uuid}/data)
   移动文件: _uploads/{uuid}/data → blobs/sha256/{xx}/{digest}
   清理目录: _uploads/{uuid}/
   ```

## 数据完整性保证

### 1. 内容寻址存储

- **不可变性**: 一旦 Blob 存储完成，内容不会改变
- **去重**: 相同内容的 Blob 自动去重，节省存储空间
- **完整性**: 通过 SHA256 digest 验证数据完整性

### 2. 原子操作

```go
// 文件移动是原子操作，确保数据一致性
os.Rename(tempPath, finalPath)
```

### 3. 临时文件隔离

- 每个上传会话使用独立的临时目录
- 上传失败时可以安全清理，不影响其他操作
- 支持并发上传而不互相干扰

## 存储空间优化

### 1. 自动去重

由于使用内容寻址存储，相同的 Blob 只存储一份：

```
# 两个镜像可能共享相同的基础层
myapp:v1.0 → layer1(digest:abc), layer2(digest:def), config(digest:ghi)
myapp:v1.1 → layer1(digest:abc), layer3(digest:jkl), config(digest:mno)

# 磁盘上只存储：abc, def, ghi, jkl, mno (共5个文件)
```

### 2. 稀疏存储支持

文件系统级别的稀疏文件支持可以进一步优化存储效率。

## 并发安全设计

### 1. 读操作并发安全

- Blob 文件一旦创建就不会修改，支持无限并发读取
- Manifest 文件同样具有不可变性

### 2. 写操作并发安全

- 使用 UUID 确保上传会话隔离
- 原子文件操作 (`os.Rename`) 确保写入安全
- 临时文件机制避免部分写入问题

### 3. 清理操作并发安全

- 标签删除只影响标签映射，不删除 Blob 数据
- 垃圾回收需要额外的机制（当前版本未实现）

## 性能特征

### 1. 读取性能

- **O(1) 访问**: 通过 digest 直接定位文件
- **文件系统缓存**: 依赖操作系统文件系统缓存
- **并发读取**: 支持高并发读取操作

### 2. 写入性能

- **流式写入**: 支持大文件的流式处理
- **批量操作**: 分片上传减少网络开销
- **原子提交**: 确保数据一致性

### 3. 空间效率

- **去重存储**: 自动去重相同内容
- **压缩支持**: 支持文件系统级别的压缩
- **增量存储**: 通过分层机制实现增量存储

## 扩展性考虑

### 1. 存储后端抽象

当前实现为文件系统存储，但架构支持扩展到其他存储后端：

```go
type StorageDriver interface {
    GetBlob(digest string) (io.ReadCloser, error)
    StatBlob(digest string) (int64, error)
    PutBlob(digest string, content io.Reader) error
    // ...
}
```

### 2. 分布式存储支持

- **分片策略**: 可以按 digest 前缀进行分片
- **副本机制**: 支持多副本存储提高可靠性
- **负载均衡**: 支持读写分离和负载均衡

### 3. 缓存层支持

- **内存缓存**: 缓存热点 Manifest 数据
- **CDN 集成**: 支持 CDN 加速 Blob 分发
- **本地缓存**: 支持本地 SSD 缓存热点数据

## 维护和监控

### 1. 存储监控指标

- **磁盘使用量**: 总存储空间和可用空间
- **文件数量**: Blob 和 Manifest 文件数量
- **访问模式**: 热点文件和访问频率

### 2. 清理策略

- **孤立 Blob 清理**: 定期清理没有被 Manifest 引用的 Blob
- **过期上传清理**: 清理长时间未完成的上传会话
- **标签清理**: 根据保留策略清理旧标签

### 3. 备份策略

- **增量备份**: 基于文件修改时间的增量备份
- **一致性备份**: 确保 Manifest 和 Blob 数据的一致性
- **恢复验证**: 定期验证备份数据的完整性

这种存储设计确保了数据的完整性、一致性和高性能，同时保持了与官方 Docker Registry 的兼容性。
