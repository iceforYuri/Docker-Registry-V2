
# 设计指导文档

本文档阐述了 Docker Registry Lite 项目的整体设计理念、架构决策和实现指导原则。

## 项目目标与定位

### 核心目标
- **API 兼容性**: 完全兼容 Docker Registry HTTP API V2 规范
- **功能完整性**: 支持容器镜像的完整推送、存储和拉取流程  
- **跨平台支持**: 同时支持 Windows 和 Linux 操作系统
- **简洁性**: 在保证核心功能的前提下，避免过度复杂的设计

### 适用场景
- ✅ **开发测试环境**: 本地容器镜像存储和分发
- ✅ **内网私仓**: 企业内部容器镜像管理
- ✅ **学习研究**: 理解 Docker Registry 工作原理
- ❌ **生产环境**: 需要额外的安全和高可用性机制

#### 1. 项目结构

一个清晰的目录结构有助于代码的组织和维护。建议采用经典的 Go 项目布局：

```
docker-registry-lite/
├── cmd/
│   └── registry/
│       └── main.go         // ✅ 程序主入口，负责组装和启动
├── internal/
│   ├── handler/            // ✅ HTTP 请求处理器 (Controller/Handler层)
│   │   ├── api.go          //    - 路由注册
│   │   ├── blobs.go        //    - Blob 相关接口的实现
│   │   └── manifests.go    //    - Manifest 相关接口的实现
│   ├── middleware/         // ✅ HTTP 中间件
│   │   └── recovery.go     //    - Panic 恢复中间件
│   ├── registry/           // ✅ 核心业务逻辑与数据模型 (Domain/Model层)
│   │   ├── errors.go       //    - 自定义错误类型
│   │   └── types.go        //    - Manifest, Blob 等核心数据结构
│   └── storage/            // ✅ 存储层 (Repository/DAL层)

```

#### 2. 技术选型与依赖库

- **HTTP 路由**: 我们可以使用 Go 标准库的 `net/http`，但为了更方便地处理路径参数（如 `<name>`, `<digest>`），推荐使用 `gorilla/mux`。它是一个轻量级且功能强大的路由库。
- **UUID 生成**: Blob 分片上传需要生成唯一的上传 ID。`github.com/google/uuid` 是事实上的标准库。
- **配置管理**: 虽然本项目简化了，但一个好的实践是使用 `viper` 或类似库来管理配置（如存储路径），但初期也可以用硬编码或环境变量。
- **日志**: 使用标准库 `log` 即可满足基本需求。

执行 `go mod init <your_module_name>` 初始化项目，并使用 `go get` 安装所需依赖。

### 第二步：设计存储层

Docker Registry 是一个**内容寻址存储（Content-Addressable Storage）**系统。这意味着所有对象（Blob、Manifest）都由其内容的哈希值（Digest）来唯一标识。

我们的文件系统存储布局应该模仿官方 Registry 的结构：

```
/var/lib/registry/      <-- 存储根目录
└── docker/
    └── registry/
        └── v2/
            ├── blobs/          // 存放所有 Blob
            │   └── sha256/
            │       ├── aa/
            │       │   └── aacec273.../
            │       │       └── data    // Blob 的实际内容
            │       └── bb/
            │           └── bb1b544c.../
            │               └── data
            └── repositories/   // 存放 Manifest 和 Tag 的链接
                └── my-app/
                    ├── _layers/
                    ├── _manifests/
                    │   ├── revisions/
                    │   │   └── sha256/
                    │   │       └── f3b4.../
                    │   │           └── link // 文件内容是 manifest 的 digest (sha256:...)
                    │   └── tags/
                    │       └── latest/
                    │           ├── current/
                    │           │   └── link // 文件内容是 tag 指向的 manifest digest
                    │           └── index/
                    └── _uploads/       // 存放未完成的上传（临时文件）
```

**关键点**:

1. **Blob 存储**: Blob 的路径由其摘要算法（sha256）、摘要值的前两个字符（用于分片目录，防止单个目录下文件过多）和完整的摘要值决定。`data` 文件包含原始二进制内容。
2. **Manifest 存储**: Manifest 本身也作为一个 Blob 存储在 `blobs` 目录下。
3. **Tag 关联**: `repositories` 目录下的 `link` 文件将一个 Tag（如 `latest`）指向一个具体的 Manifest Digest。

我们需要在 `internal/storage/filesystem.go` 中实现一系列方法来操作这个文件结构，例如：

- `StatBlob(digest string)`: 检查 Blob 是否存在并返回其大小。
- `GetBlob(digest string)`: 读取并返回 Blob 内容。
- `StartUpload()`: 在 `_uploads` 目录下创建一个临时文件并返回一个唯一的上传 ID。
- `AppendChunk(uploadID string, chunk []byte)`: 向临时文件追加数据。
- `CommitUpload(uploadID string, finalDigest string)`: 校验临时文件的完整性，如果成功，将其移动到 `blobs` 目录下的最终位置。
- `PutManifest(repo, reference, contentType string, manifest []byte)`: 存储 Manifest 并创建 Tag 链接。
- `GetManifest(repo, reference string)`: 获取 Manifest。

### 第三步：实现 API Endpoints

现在我们逐一实现 API 文档中定义的接口。以下是 `docker push` 流程涉及的核心接口：

#### 1. `GET /v2/` - API 版本检查

这是客户端发出的第一个请求，用于确认 Registry 是否兼容 V2 API。

- **路径**: `/v2/`
- **方法**: `GET`
- **逻辑**:
  - 无需任何处理。
  - 返回 `200 OK`。
  - 在响应头中设置 `Docker-Distribution-Api-Version: registry/2.0`。

#### 2. Blob 分片上传

这是最复杂的部分，涉及多个状态相关的请求。我们需要一个地方来跟踪上传进度，一个简单的 `map[string]UploadState` 即可（key 是 Upload ID）。

```go
// internal/registry/types.go
type UploadState struct {
    UUID       string
    Path       string // 临时文件路径
    Repository string
    Size       int64
    StartedAt  time.Time
}
```

##### a. `POST /v2/<name>/blobs/uploads/` - 开始上传

- **路径**: `/v2/<name>/blobs/uploads/`
- **方法**: `POST`
- **逻辑**:
  1. 调用存储层的 `StartUpload()`，它会生成一个 UUID 并在 `_uploads` 目录创建临时文件。
  2. 记录这个新的上传状态。
  3. 返回 `202 Accepted`。
  4. 响应头：
     - `Location`: 指向分片上传的 URL，如 `/v2/<name>/blobs/uploads/<uuid>`。
     - `Docker-Upload-UUID`: `<uuid>`。
     - `Range`: `0-0` (表示已接收 0 字节)。

##### b. `PATCH /v2/<name>/blobs/uploads/<uuid>` - 上传分片

- **路径**: `/v2/<name>/blobs/uploads/<uuid>`
- **方法**: `PATCH`
- **逻辑**:
  1. 根据 `uuid` 查找上传状态。如果找不到，返回 `404 Not Found`。
  2. 读取请求体（即数据块）。
  3. 校验 `Content-Type` 必须是 `application/octet-stream`。
  4. 调用存储层的 `AppendChunk()` 将数据块写入临时文件。
  5. 更新 `UploadState` 中的 `Size`。
  6. 返回 `202 Accepted`。
  7. 响应头：
     - `Location`: 同上。
     - `Docker-Upload-UUID`: `<uuid>`。
     - `Range`: `0-<new_size-1>`。

##### c. `PUT /v2/<name>/blobs/uploads/<uuid>?digest=<digest>` - 完成上传

- **路径**: `/v2/<name>/blobs/uploads/<uuid>`
- **方法**: `PUT`
- **逻辑**:
  1. 根据 `uuid` 查找上传状态。如果找不到，返回 `404 Not Found`。
  2. 从 URL query 中获取 `digest` 参数。如果缺少，返回 `400 Bad Request`。
  3. **完整性校验**: 计算整个临时文件的 SHA256 digest。
  4. 将计算出的 digest 与客户端提供的 `digest` 参数进行比较。
     - **如果不匹配**: 删除临时文件，清理上传状态，返回 `400 Bad Request`，并附带错误信息。
     - **如果匹配**: 调用存储层的 `CommitUpload()`，将临时文件移动到最终的 content-addressable 位置。
  5. 清理上传状态。
  6. 返回 `201 Created`。
  7. 响应头：
     - `Location`: 指向 Blob 的最终 URL，如 `/v2/<name>/blobs/<digest>`。
     - `Docker-Content-Digest`: `<digest>`。

#### 3. `HEAD /v2/<name>/blobs/<digest>` - 检查 Blob 是否存在

客户端在上传前会用此接口检查 Blob 是否已存在，以避免重复上传。

- **路径**: `/v2/<name>/blobs/<digest>`
- **方法**: `HEAD`
- **逻辑**:
  1. 调用存储层的 `StatBlob(digest)`。
  2. 如果存在，返回 `200 OK`，并设置 `Content-Length` 和 `Docker-Content-Digest` 头。
  3. 如果不存在，返回 `404 Not Found`。

#### 4. `PUT /v2/<name>/manifests/<reference>` - 上传 Manifest

当所有 layers (blobs) 都上传完毕后，客户端会上传 manifest 文件。

- **路径**: `/v2/<name>/manifests/<reference>` (`reference` 可以是 tag 或 digest)
- **方法**: `PUT`
- **逻辑**:
  1. 读取请求体（Manifest JSON）。
  2. **校验 Content-Type**: 必须是 `application/vnd.docker.distribution.manifest.v2+json` 或 `application/vnd.docker.distribution.manifest.list.v2+json`。如果不是，返回 `400 Bad Request`。
  3. **完整性校验**: 计算请求体的 SHA256 digest。如果 `reference` 本身是一个 digest，那么它必须与计算出的 digest 匹配。
  4. 解析 Manifest JSON。
  5. **依赖校验**: 遍历 Manifest 中引用的所有 `layers` 和 `config` 的 digest，逐一调用 `StatBlob()` 确认它们都已存在于 Registry 中。
     - 如果有任何一个 Blob 不存在，返回 `400 Bad Request`，并在响应体中明确指出哪个 Blob 缺失。
  6. 所有校验通过后，调用存储层的 `PutManifest()`。这个方法会将 Manifest 内容本身存为一个 Blob，并创建或更新 tag->digest 的链接文件。
  7. 返回 `201 Created`。
  8. 响应头：
     - `Location`: 指向 Manifest 的 URL，如 `/v2/<name>/manifests/<digest>`。
     - `Docker-Content-Digest`: Manifest 的 digest。

### 第四步：错误处理与健壮性

这是项目中非常重要的一环。

1. **统一的错误响应**: 根据 API 规范，错误应该以固定的 JSON 格式返回。

   ```json
   {
     "errors": [
       {
         "code": "MANIFEST_INVALID",
         "message": "manifest invalid",
         "detail": "..."
       }
     ]
   }
   ```

   可以创建一个辅助函数 `writeErrorResponse(w, code, errCode, message)` 来生成这种格式的响应。
2. **Panic恢复**: 使用一个中间件（`middleware/recovery.go`）来捕获 HTTP handler 中的 `panic`，记录错误日志，并返回 `500 Internal Server Error`，而不是让整个程序崩溃。

   ```go
   func Recovery(next http.Handler) http.Handler {
       return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
           defer func() {
               if err := recover(); err != nil {
                   log.Printf("panic recovered: %v", err)
                   // Write a generic 500 error response
                   writeErrorResponse(w, http.StatusInternalServerError, "INTERNAL_ERROR", "An unexpected error occurred.")
               }
           }()
           next.ServeHTTP(w, r)
       })
   }
   ```
3. **处理 400 和 404**:

   - **404 (Not Found)**: 当请求的资源（如 Blob, Manifest, Upload session）不存在时返回。
   - **400 (Bad Request)**: 当客户端请求不合法时返回，例如：
     - 提供了错误的 `Content-Type`。
     - Manifest 格式错误。
     - 上传 Blob 时 digest 校验失败。
     - 上传 Manifest 时其引用的 Blob 不存在。

### 第五步：组装与运行

在 `cmd/registry/main.go` 中，我们将所有部分组合起来：

1. 初始化存储层实例。
2. 初始化路由 (`gorilla/mux`)。
3. 注册所有 API 路由及其对应的 Handler 函数。
4. 将路由包裹在我们的 `Recovery` 中间件中。
5. 启动 `http.Server` 监听端口。

```go
// cmd/registry/main.go (简化示例)
func main() {
    storageRoot := "/var/lib/my-registry" // 应该来自配置
    storageDriver := storage.NewFileSystemStorage(storageRoot)

    r := mux.NewRouter()

    // 注册路由
    handler.RegisterRoutes(r, storageDriver) // 假设我们把路由注册逻辑封装起来了

    // 添加中间件
    loggedRouter := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        log.Printf("%s %s %s", r.RemoteAddr, r.Method, r.URL)
        r.ServeHTTP(w, r)
    })
  
    // 注意中间件的包裹顺序
    finalHandler := middleware.Recovery(loggedRouter(r))

    log.Println("Starting registry server on :5000")
    if err := http.ListenAndServe(":5000", finalHandler); err != nil {
        log.Fatalf("Failed to start server: %v", err)
    }
}
```

### 第六步：测试

在 Linux (Debian 13) 环境中，你可以使用真实的 Docker 客户端来测试你的 Registry 服务。

1. **运行你的 Go 程序**。
2. **配置 Docker Daemon**:
   编辑 `/etc/docker/daemon.json` (如果不存在则创建)，添加你的 Registry 地址为不安全的 registry（因为我们没有实现 TLS/Auth）。

   ```json
   {
     "insecure-registries" : ["localhost:5000"]
   }
   ```

   然后重启 Docker 服务: `sudo systemctl restart docker`。
3. **进行 push 和 pull 操作**:

   ```bash
   # 拉取一个小型镜像用于测试
   docker pull hello-world

   # 给镜像打上指向你本地 registry 的 tag
   docker tag hello-world localhost:5000/my-test-image:latest

   # 推送镜像到你的 registry
   # 观察你的 Go 程序日志，你会看到一系列的 API 请求
   docker push localhost:5000/my-test-image:latest

   # （可选）删除本地镜像，然后从你的 registry 拉取回来
   docker rmi localhost:5000/my-test-image:latest
   docker pull localhost:5000/my-test-image:latest
   ```
